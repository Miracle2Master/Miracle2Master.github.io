# LangChain 核心概念

---

## 一、LangChain 定位

LangChain 是连接 LLM 与外部数据和工具的胶水框架。LLM 本身只能基于训练数据生成文本，对训练截止日期之后的信息一无所知。LangChain 负责在 LLM 回答之前，帮它找到相关资料、调用外部工具、拼到 Prompt 里。

类比：LLM 是一个"记忆力超强但被锁在房间里的人"，LangChain 是"递纸条、递工具的那个人"。

---

## 二、基础 RAG 架构

### 2.1 核心流程

RAG（检索增强生成）是 LangChain 最常用的场景，核心链路包含五个环节：

```
文档加载 → 文本切分 → 向量化 → 向量存储 → 检索召回 → 拼 Prompt → LLM 生成
```

### 2.2 五大组件

| 组件 | 作用 | 类比 |
|------|------|------|
| Document Loader | 读取 PDF/Word/TXT 等文件 | 打开文件 |
| Text Splitter | 把长文档切成小段 | 把书撕成一页一页 |
| Embeddings | 把文字转成向量（数学数组），语义越接近向量越相似 | 把文字翻译成计算机能算的语言 |
| Vector Store | 存储向量 + 原文，支持相似度搜索 | 图书馆的索引卡片柜 |
| Retriever | 根据问题检索最相关的片段 | 图书管理员帮你找书 |

### 2.3 四种分块策略

- **递归分块**（RecursiveCharacterTextSplitter）：通用方案，按段落→句子→字符的优先级逐级切分
- **语义分块**（SemanticChunker）：AI 判断语义自然断点，保留逻辑完整性
- **标题分块**（MarkdownHeaderTextSplitter）：按 Markdown 标题层级（H1/H2/H3）分块，保留文档结构
- **句子分块**（SpacyTextSplitter）：NLP 断句后分块，对中文有更好的断句能力

### 2.4 数据清洗管线

LangChain 提供 Document Transformer 机制，数据进入向量库之前经过清洗管线串联处理：

- HTML 标签清洗（BeautifulSoupTransformer）
- 相似内容去重（EmbeddingsRedundantFilter，相似度超阈值只保留一条）
- 长上下文重排序（LongContextReorder，重要内容放两端，克服 LLM 的"Lost in the Middle"问题）

## 三、高级检索策略

### 3.1 多路召回

基础 RAG 只做向量检索，高级 RAG 同时走多路召回再融合：

- **向量检索**：语义相似，找"意思相近"的内容
- **BM25 检索**：关键词匹配，找"出现相同词"的内容
- **融合**（Ensemble Retriever）：两路结果加权合并去重，各取所长

### 3.2 重排序（Rerank）

向量检索和 BM25 属于粗排（速度快但精度有限），召回 20 条候选后再用 Rerank 模型做精排，只保留最相关的 3-5 条送给 LLM。精排用 Cross-Encoder 架构，同时对问题和文档打分，比向量相似度准得多。

### 3.3 自查询检索（Self-Querying）

用户用自然语言描述筛选条件时，LLM 自动将"2025 年以后的深度学习论文"拆解为结构化过滤（year >= 2025）加语义查询（"深度学习"），同时作用于元数据过滤和向量检索。

---

## 四、对话记忆管理

LLM 本身是无状态的，每次调用独立。LangChain 提供四种记忆策略解决多轮对话问题：

| 策略 | 原理 | 适用场景 |
|------|------|---------|
| ConversationBufferMemory | 记住全部历史，每次全量传入 | 短对话 |
| ConversationSummaryMemory | LLM 自动摘要历史，只传摘要 | 长对话（省 token） |
| ConversationBufferWindowMemory | 只记最近 K 轮 | 关注近期上下文 |
| VectorStoreRetrieverMemory | 历史存向量库，用到才检索 | 超长对话 |

## 五、ReAct 推理模式

### 5.1 三种回答模式对比

**标准回答**：LLM 直接用训练数据回答，无外部信息源。适合常识性问题。

**Chain of Thought（思维链）**：LLM 在脑子中分步推理，但不调用任何工具。适合纯逻辑问题（数学、推理）。

**ReAct**：Reasoning（推理）+ Acting（行动）交替进行。LLM 不只是"想"，还会"动手"——调用外部工具获取信息，根据返回结果继续思考，最终给出有依据的答案。

### 5.2 ReAct 的核心循环

```
Thought（思考当前需要什么信息）
    ↓
Action（选择并调用一个工具）
    ↓
Observation（观察工具返回的结果）
    ↓
Thought（信息够了吗？不够继续循环）
    ↓
Final Answer（够了，给出最终答案）
```

LLM 的角色从"回答者"变成了"决策者"——自主判断需要什么信息、哪个工具能拿到、拿到了够不够、不够再查。

### 5.3 一次完整的 ReAct 执行过程

用户提问："找 3 篇 2024 年关于大模型微调的论文，总结方法优劣"

| 轮次 | Thought（思考） | Action（行动） | Observation（观察） |
|------|----------------|---------------|-------------------|
| 1 | 需要先按条件筛选论文 | 调元数据查询工具 | 返回 10 篇候选 |
| 2 | 挑最相关的 3 篇 | 调论文搜索工具 | 返回 3 篇精华 |
| 3 | 逐篇读内容 | 调读取全文工具 | 论文 A 全文 |
| 4 | 继续读 | 调读取全文工具 | 论文 C 全文 |
| 5 | 继续读 | 调读取全文工具 | 论文 F 全文 |
| 6 | 信息足够，整理对比 | — | 输出对比表格 |

整个过程 LLM 自主规划、自主调度、自主收敛。

### 5.4 ReAct 如何实现

LangChain 用 Prompt 格式约束让 LLM 按 `Thought → Action → Observation` 输出，LangChain 解析输出后真的调用工具，把结果作为 Observation 喂回去，形成循环。`AgentExecutor` 控制最大循环次数（如 10 轮），防止死循环。

### 5.5 ReAct 与基础 RAG 的对比

| | 基础 RAG | ReAct Agent |
|------|---------|------------|
| 工具调用 | 0 次，固定流程 | N 次，自主决策 |
| 流程 | 检索→拼 Prompt→回答 | 思考→调工具→观察→再思考→... |
| 适用场景 | 简单问答 | 需要多步推理的复杂查询 |
| 耗时 | 1-2 秒 | 3-10 秒 |
| LLM 角色 | 回答者 | 决策者 + 回答者 |

## 六、Agent 智能体

### 6.1 Agent 的完整架构

Agent = LLM + 工具集 + 推理模式（ReAct）。LLM 作为"大脑"判断何时调用哪个工具，工具作为"手脚"执行具体操作。用户可以给 Agent 绑定任意工具（搜索、读文件、查数据库、发邮件），Agent 自主完成多步骤的复杂任务。

### 6.2 RAG 和 Agent 的关系

RAG 是 Agent 的一种特定形态（工具只有检索器），Agent 是 RAG 的超集（可以有任意工具）。一个完整的 Agent 可以同时具备搜索论文、读取全文、对比分析、输出表格的能力。

---

## 七、可观测性

LangSmith 是 LangChain 官方的调试和监控平台。所有 LangChain 调用自动上报全链路 Trace，可视化展示每次调用的输入输出、每一步耗时、Token 消耗和费用。用于排查检索链中各环节的质量问题（哪一步慢了、哪一步召回不准）。

### 问题：

  1. ReAct 中 LLM 自主决策调用哪个工具——如果 LLM 选错了工具怎么办？有没有机制能防止它"乱来"？
  2. 向量检索 + BM25 + Rerank 三级流水线中，每一级的"截断数量"（粗排召回 20 条、精排保留 5
    条）如何确定？这个数字对最终效果的影响有多大？
  3. RAG 把资料拼到 Prompt 里给 LLM 参考，但如果资料本身包含矛盾的结论（比如两篇论文对同一方法给出相反评价），LLM
    会怎么处理？这种"知识冲突"是 RAG 的一个核心难题。
